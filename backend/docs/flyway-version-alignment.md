# 장소 마이그레이션 번호 조정

회원·관심 장소 마이그레이션 번호를 유지하고 대표 사진 V8 중복을 해소한다. 기존 SQL 본문과 체크섬은 변경하지 않는다.

- V4: 회원 테이블 (#9).
- V5: 인증 버전 (#13).
- V6: 비밀번호 재설정 토큰 (#13).
- V7: `create_tour_api_import_tracking`.
- V8: `create_favorites` (#14).
- V9: `create_place_representative_image` (기존 사진 V8).
- V10: `create_place_operating_info` (운영 정보 수집·표시, 기존 V9).

회원 → 재설정 → 장소 수집 → 관심 장소 → 사진 → 운영 정보 순서로 적용한다. 아직 없는 파일이나 성공 이력을 임의로 만들지 않는다.

## 개인 DB 처리

빈 DB는 평소처럼 실행한다. 사진 V8·운영 정보 V9를 적용한 개인 DB는 백업·복원을 확인한 뒤, 실제 스크립트명과 체크섬이 일치하는 두 이력만 사진 V9·운영 정보 V10으로 맞춘다. 적용 순서와 체크섬, 장소·사진·운영 정보 데이터는 유지한다. 이 수동 조정을 공유 DB에 그대로 실행하지 않는다.

이 개인 DB에 빠진 회원 V4~V6·관심 장소 V8은 검토와 백업 후 한 번만 `--spring.flyway.out-of-order=true`로 실제 SQL을 적용한다. 정상 검증 후 다음 실행에서는 옵션을 제거한다. 공통 설정·CI에 상시 켜지 않는다.

## 배포 DB 처리

배포 DB 접근·수정은 이번 로컬 조정에 포함되지 않는다. 담당자가 배포 전에 `flyway_schema_history`의 실제 버전·스크립트를 확인해야 한다. 이미 사진 V8을 적용한 DB라면 번호 변경만 배포하지 말고 백업과 별도 이력 정합성 작업을 먼저 계획한다. 새 V8은 관심 장소 SQL이며, 사진 V8을 관심 장소로 바꿔 기록하면 안 된다.

체크섬을 숨기기 위한 repair, 전체 이력 초기화, 테이블 삭제는 하지 않는다.
