# 미공유 장소 마이그레이션 번호 조정

회원가입·로그인 PR의 V4와 충돌하지 않도록, 아직 PR로 공유하지 않은 장소 후속 마이그레이션의 번호를 조정했다. SQL 본문과 V1~V3는 변경하지 않는다.

- V4: 회원 기능용으로 예약. 해당 PR이 머지되기 전에는 이 브랜치에 파일이 없다.
- V5: `create_tour_api_import_tracking` (기존 V4).
- V6: `create_place_representative_image` (기존 V5, 사진 브랜치부터 포함).
- V7: `create_place_operating_info` (기존 V6, 운영 정보 브랜치부터 포함).

## DB별 적용

빈 DB 또는 V1~V3까지만 적용한 DB는 평소처럼 실행한다. 아직 없는 V4의 이력을 임의로 넣지 않는다.

기존 장소 V4~V6를 적용한 개발자 개인 DB는 파일명만 변경하면 검증에 실패한다. 이 경우 전체 DB 백업과 별도 DB 복원을 확인한 다음, 기존 SQL의 내용·체크섬이 같다는 전제로 해당 세 이력의 `version`과 `script`만 V5~V7로 맞춘다. 장소 데이터와 `installed_rank`, `checksum`, `success`는 유지한다. 공유·운영 DB에 일반적인 마이그레이션 절차로 사용하면 안 된다.

이 개인 DB가 V7까지 적용된 뒤 실제 회원 V4 파일이 머지되면, 낮은 버전이 나중에 들어오는 상황이다. 회원 V4 내용을 검토하고 백업한 후, 그 실행에 한해서 `--spring.flyway.out-of-order=true`를 전달해 실제 V4를 적용한다. 정상 적용과 Flyway 검증을 확인한 뒤 다음 실행부터 옵션을 제거한다. 공통 설정이나 CI에서 `out-of-order`를 상시 활성화하지 않는다. 빈 DB는 이 옵션이 필요 없다.

체크섬 불일치를 숨기기 위한 `repair`, 테이블 삭제, 전체 이력 초기화는 사용하지 않는다.
